# 아키텍처 의사결정 기록 (ADR)

이 문서는 공유 모빌리티 플랫폼에서 내린 주요 아키텍처 의사결정을 기록하며, 맥락, 근거 및 트레이드오프를 포함합니다.

> **참고**: 원본 영문 문서는 `architecture-decisions.md`에서 확인할 수 있습니다.

---

## ADR-001: 마이크로서비스 아키텍처

**상태**: 승인됨
**날짜**: 2024-01
**의사결정자**: 아키텍처 팀

### 맥락
서로 다른 데이터 액세스 패턴(트랜잭션형 vs 시계열)을 가진 확장 가능한 차량 공유 플랫폼을 구축해야 합니다.

### 의사결정
5개의 독립 서비스로 마이크로서비스 아키텍처 채택:
- User Service (인증, 프로필)
- Vehicle Service (재고, IoT)
- Rental Service (트랜잭션, Saga)
- Location Service (GPS 추적)
- Battery Service (텔레메트리 모니터링)

### 근거
1. **독립적인 확장**: Location/Battery 서비스는 User/Vehicle의 4배 용량 필요
2. **기술 다양성**: 트랜잭션에는 PostgreSQL, 시계열에는 MongoDB 사용
3. **팀 자율성**: 서로 다른 팀이 서로 다른 서비스를 소유 가능
4. **장애 격리**: Battery Service 다운 시에도 대여에 영향 없음

### 결과
**긍정적**:
- 서비스별 수평 확장
- 다중 언어 지속성 (SQL + NoSQL)
- 독립적인 배포 주기

**부정적**:
- 분산 시스템 복잡성
- 이벤트 드리븐 통신 필요
- 분산 트랜잭션을 위한 Saga 패턴 필요

### 고려한 대안
**모놀리식 아키텍처**: 더 간단하지만 컴포넌트를 독립적으로 확장할 수 없음
**모듈식 모놀리스**: 순수 모놀리스보다 낫지만 여전히 단일 배포 단위

## ADR-002: Kafka를 사용한 이벤트 드리븐 아키텍처

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
마이크로서비스가 강한 결합과 동기 REST 호출 없이 통신해야 합니다.

### 의사결정
14개의 도메인 이벤트 토픽으로 Apache Kafka를 이벤트 백본으로 사용.

### 근거
1. **느슨한 결합**: 서비스는 서로를 알 필요 없고 이벤트만 알면 됨
2. **비동기 처리**: 대여 완료가 차량 업데이트를 기다리지 않음
3. **이벤트 재생**: 7일 보존으로 장애 복구 가능
4. **확장성**: vehicleId별 파티셔닝으로 병렬 처리 가능

### 결과
**긍정적**:
- 서비스 독립적 확장 가능
- 장애 격리 (소비자 다운 시 발행자에 영향 없음)
- 감사 추적 (불변 이벤트 로그)

**부정적**:
- 최종 일관성 (즉시 일관성 아님)
- 멱등성 처리 필요
- 운영 복잡성 (Kafka 클러스터 관리)

### 고려한 대안
**RabbitMQ**: 더 간단하지만 처리량 낮고 이벤트 소싱에 적합하지 않음
**AWS SNS/SQS**: 클라우드 종속적, 벤더 락인
**REST API**: 강한 결합, 동기식, 이벤트 재생 없음

## ADR-003: Database Per Service 패턴

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
마이크로서비스는 강한 결합을 피하기 위해 데이터베이스를 공유하지 않아야 합니다.

### 의사결정
각 서비스가 자체 데이터베이스 소유:
- User/Vehicle/Rental → PostgreSQL (별도 인스턴스)
- Location/Battery → MongoDB (별도 데이터베이스)
- 모든 서비스 → Redis (캐싱/Saga용 공유)

### 근거
1. **서비스 자율성**: 스키마 변경이 다른 서비스에 영향 없음
2. **기술 적합성**: ACID용 PostgreSQL, 시계열용 MongoDB
3. **독립적인 확장**: 각 데이터베이스가 독립적으로 확장

### 결과
**긍정적**:
- 서비스 간 SQL 조인 없음 (경계 강제)
- 서비스별 최적 데이터베이스 선택
- 독립적인 백업/복원 전략

**부정적**:
- 데이터 중복 (차량 위치가 Vehicle과 Location 서비스 모두에)
- 분산 트랜잭션에 Saga 패턴 필요
- 인프라 비용 증가 (6개 데이터베이스)

## ADR-004: 분산 트랜잭션을 위한 Saga 패턴

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
대여가 여러 서비스(Rental, Vehicle, Payment, Location)에 걸쳐 있지만 분산 트랜잭션 없음.

### 의사결정
`RentalSagaOrchestrator`로 Saga 오케스트레이션 패턴 사용.

### 근거
1. **마이크로서비스 호환**: 2PC(Two-Phase Commit) 불필요
2. **명확한 롤백**: 보상 액션이 잘 정의됨
3. **상태 지속성**: 장애 허용을 위해 Redis에 Saga 상태 저장

### 결과
**긍정적**:
- 대여 도메인에 최종 일관성 허용 가능
- 새로운 Saga 단계 추가 용이
- 명확한 실패 처리

**부정적**:
- 보상 로직의 복잡성
- 부분 실패가 사용자에게 보임
- 재시도 메커니즘 필요

### 고려한 대안
**Two-Phase Commit (2PC)**: 마이크로서비스에서 지원 안 됨, 높은 지연
**Choreography Saga**: 상태 추적 어렵고 중앙 조정자 없음

## ADR-005: 시계열 데이터를 위한 MongoDB

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
Location 및 Battery 서비스는 대용량 시계열 텔레메트리 데이터를 저장합니다.

### 의사결정
Location 및 Battery 서비스에 MongoDB 사용.

### 근거
1. **지리공간 인덱싱**: 근접 쿼리를 위한 네이티브 2dsphere 인덱스
2. **쓰기 처리량**: 샤딩으로 10K+ 쓰기/초
3. **스키마 유연성**: IoT 페이로드 다양함 (전압, 온도 등)
4. **시계열**: 효율적인 시간 범위 쿼리

### 결과
**긍정적**:
- 빠른 지리공간 쿼리 (1km 내 차량 찾기)
- 높은 삽입 성능 (추가 전용 데이터)
- 샤딩을 통한 수평 확장

**부정적**:
- ACID 트랜잭션 없음 (텔레메트리에는 허용 가능)
- 지리공간 쿼리 학습 곡선
- PostgreSQL과 다름 (다중 언어 지속성)

### 고려한 대안
**PostGIS를 사용한 PostgreSQL**: 더 친숙하지만 쓰기 처리량 낮음
**TimescaleDB**: 시계열에 좋지만 네이티브 지리공간 인덱스 없음
**Cassandra**: 더 높은 처리량이지만 지리공간 지원 없음

## ADR-006: 캐싱 및 Saga 상태를 위한 Redis

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
Saga 상태, 위치 캐시 및 멱등성 추적에 대한 낮은 지연 액세스 필요.

### 의사결정
다음 용도로 Redis 사용:
- Saga 상태 (24시간 TTL)
- 위치 캐시 (30초 TTL)
- 멱등성 추적 (7일 TTL)

### 근거
1. **성능**: 밀리초 미만 지연
2. **TTL 지원**: 오래된 데이터 자동 정리
3. **원자적 연산**: 멱등성을 위한 SETNX, 카운터를 위한 INCR

### 결과
**긍정적**:
- 빠른 Saga 상태 액세스 (~1ms vs PostgreSQL 30ms)
- 위치 캐시가 MongoDB 읽기를 95% 감소
- 데이터베이스 오버헤드 없는 멱등성

**부정적**:
- Redis 크래시 시 데이터 손실 (Saga 상태는 이벤트로부터 재생성)
- 메모리 제한 (캐시 퇴출 필요)
- 내구성 없음 (프로덕션에서 Redis 지속성 사용)

### 고려한 대안
**Saga용 PostgreSQL**: 내구성 있지만 느리고 TTL 없음
**캐시용 Memcached**: 지속성 없고 기능 적음

## ADR-007: Idempotent Consumer 패턴

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
Kafka는 at-least-once 전달을 보장하여 중복 이벤트를 유발할 수 있습니다.

### 의사결정
Redis SETNX로 `IdempotencyChecker` 구현.

### 근거
1. **정확히 한 번 의미론**: 중복 처리 방지
2. **원자적 체크-앤-셋**: Redis SETNX가 원자성 제공
3. **TTL 기반 정리**: 7일 TTL이 메모리와 재생 윈도우 균형

### 결과
**긍정적**:
- Kafka at-least-once 전달에 안전
- 차량 상태 중복 업데이트 없음
- TTL을 통한 자동 정리

**부정적**:
- 이벤트 처리에 Redis 의존성
- 7일 윈도우 (그보다 오래된 이벤트는 재처리 가능)

## ADR-008: IoT 통합을 위한 Hexagonal 아키텍처

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
Vehicle Service가 IoT 장치와 통합되지만 벤더가 변경될 수 있습니다.

### 의사결정
`IoTDevicePort` 인터페이스로 Ports & Adapters 패턴 사용.

### 근거
1. **벤더 독립성**: IoT 제공업체 교체 용이
2. **테스트 가능성**: 실제 장치 없이 MockAdapter 사용
3. **의존성 역전**: VehicleService가 구현이 아닌 인터페이스에 의존

### 결과
**긍정적**:
- @Qualifier를 통해 MockAdapter ↔ HttpAdapter ↔ MQTTAdapter 교체
- 단위 테스트에 실제 IoT 장치 불필요
- 도메인과 인프라 간 명확한 경계

**부정적**:
- 추가 추상화 계층
- 여러 어댑터 유지 관리 필요

## ADR-009: 마이크로서비스를 위한 Spring Boot

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
빠른 마이크로서비스 개발을 위한 Java 프레임워크 필요.

### 의사결정
모든 서비스에 Spring Boot 3.x 사용.

### 근거
1. **생산성**: 자동 구성, 스타터 의존성
2. **생태계**: Spring Data, Spring Security, Spring Kafka
3. **관찰 가능성**: 헬스 체크, 메트릭을 위한 Actuator

### 결과
**긍정적**:
- 빠른 개발 (최소 보일러플레이트)
- 성숙한 생태계 (검증된 라이브러리)
- 프로덕션 준비 (헬스 체크, 메트릭)

**부정적**:
- 더 높은 메모리 사용량 (Micronaut, Quarkus 대비)
- 느린 시작 시간 (네이티브 컴파일 대비)

### 고려한 대안
**Micronaut**: 더 낮은 메모리, 빠른 시작이지만 작은 생태계
**Quarkus**: 네이티브 컴파일이지만 더 복잡
**Node.js**: I/O에 빠르지만 강한 타입 부족

## ADR-010: 인증을 위한 JWT

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
마이크로서비스를 위한 상태 비저장 인증 필요.

### 의사결정
User Service가 발급하는 JWT 토큰 사용 (24시간 만료).

### 근거
1. **상태 비저장**: 세션 저장소 불필요
2. **분산**: 각 서비스가 독립적으로 토큰 검증
3. **클레임 기반**: 토큰에 사용자 역할, ID 포함

### 결과
**긍정적**:
- 확장 가능 (세션 저장소 없음)
- 빠른 검증 (서명 체크)
- API Gateway와 작동

**부정적**:
- 토큰 철회 어려움 (블랙리스트 필요)
- 토큰에 민감한 데이터 (base64 인코딩, 암호화 안 됨)
- 세션 ID보다 김 (대역폭 오버헤드)

### 고려한 대안
**세션 쿠키**: 중앙집중식 세션 저장소(Redis) 필요
**OAuth2**: 내부 서비스에는 과도

## ADR-011: 로컬 개발을 위한 Docker Compose

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
팀 전체에서 일관된 개발 환경 필요.

### 의사결정
모든 인프라(PostgreSQL, MongoDB, Redis, Kafka)에 Docker Compose 사용.

### 근거
1. **일관성**: 모든 개발자에게 동일한 환경
2. **격리**: 전역 설치 없음 (PostgreSQL, MongoDB 등)
3. **오케스트레이션**: `docker-compose up`으로 모든 서비스 시작

### 결과
**긍정적**:
- "내 컴퓨터에서는 작동함" 문제 없음
- 쉬운 온보딩 (한 명령으로 시작)
- 프로덕션과 유사한 환경 (컨테이너화)

**부정적**:
- Docker 지식 필요
- 더 높은 리소스 사용량 (모든 서비스 실행)
- 프로덕션 배포 아님 (Kubernetes 사용)

## ADR-012: 수동 Kafka Acknowledgment

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
Kafka 소비자 오프셋이 커밋되는 시점에 대한 제어 필요.

### 의사결정
수동 확인 모드(`AckMode.MANUAL`) 사용.

### 근거
1. **트랜잭션 안전성**: DB 쓰기 성공 후 확인
2. **실패 처리**: 처리 실패 시 커밋하지 않음
3. **멱등성 통합**: 멱등성 체크 후 확인

### 결과
**긍정적**:
- 메시지 손실 없음 (처리 실패 시 재전달)
- 커밋 타이밍에 대한 명시적 제어
- 멱등성 패턴과 작동

**부정적**:
- `acknowledgment.acknowledge()` 명시적 호출 필요
- 확인을 잊으면 소비자 지연 위험

## ADR-013: 동시 업데이트를 위한 낙관적 잠금

**상태**: 승인됨
**날짜**: 2024-01

### 맥락
여러 요청이 동일한 차량/대여를 동시에 업데이트할 수 있습니다.

### 의사결정
낙관적 잠금을 위해 JPA `@Version` 사용.

### 근거
1. **잠금 없음**: 비관적 잠금보다 나은 동시성
2. **손실된 업데이트 방지**: 마지막 쓰기 우선 문제 방지
3. **자동**: JPA가 version 필드 관리

### 결과
**긍정적**:
- 높은 동시성 (데이터베이스 잠금 없음)
- 데이터 손상 방지
- 재시도 로직이 버전 충돌 처리

**부정적**:
- 클라이언트가 충돌 시 재시도해야 함
- 높은 경합 시나리오에 적합하지 않음

### 고려한 대안
**비관적 잠금**: 낮은 동시성, 데드락 위험
**잠금 없음**: 손실된 업데이트 가능
