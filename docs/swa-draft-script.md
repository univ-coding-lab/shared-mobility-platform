## 📌 슬라이드 3: 현재 문제점 (As-Is) (3분)

이제 공유 모빌리티 시스템이 직면한 구체적인 문제점들을 살펴보겠습니다.

**[문제 1: 실시간 차량 상태 관리의 어려움]**

첫 번째 문제는 실시간 차량 상태 관리의 어려움입니다.

공유 킥보드 서비스를 예로 들어보겠습니다. 서울 시내에만 약 1만 대 이상의 공유 킥보드가 운영되고 있습니다. 이 모든 차량의 위치, 배터리 상태, 대여 가능 여부를 실시간으로 추적하고 업데이트해야 합니다.

하지만 현재 많은 시스템에서는 데이터 업데이트에 지연이 발생합니다. 사용자가 앱에서 "대여 가능"으로 표시된 킥보드를 찾아갔는데, 막상 가보니 이미 다른 사람이 대여해서 없거나, 배터리가 부족한 경우가 발생합니다. 

이는 사용자 경험을 크게 해치는 문제입니다. 실제로 공유 모빌리티 업체들의 가장 큰 고객 불만 사항 중 하나가 바로 이 "유령 차량" 문제입니다.

또한 배터리 부족 차량을 사전에 파악하지 못해, 사용자가 대여한 후 얼마 가지 못해 멈추는 경우도 발생합니다. 이는 서비스 신뢰도를 떨어뜨리는 심각한 문제입니다.

**[문제 2: 확장성 제한]**

두 번째는 확장성의 제한입니다.

공유 모빌리티 서비스는 시간대와 지역에 따라 트래픽이 극심하게 변동합니다. 출퇴근 시간대, 특히 지하철역 주변에서는 대여 요청이 집중됩니다. 반면 심야 시간대에는 트래픽이 거의 없습니다.

만약 모든 기능이 하나로 통합된 시스템이라면, 출퇴근 시간대의 대여 트래픽을 처리하기 위해 전체 시스템의 리소스를 확장해야 합니다. 

예를 들어, 대여 서비스만 부하가 높아도, 위치 조회, 배터리 관리, 사용자 인증 등 모든 기능을 포함한 전체 시스템을 확장해야 하는 겁니다. 이는 막대한 리소스 낭비입니다.

또한 차량 수가 1만 대에서 5만 대로 증가하면, 시스템 전체의 성능이 선형적으로 저하됩니다. 부분적인 확장이 불가능하기 때문입니다.

**[문제 3: 장애 전파 위험]**

세 번째는 장애 전파의 위험입니다.

통합된 시스템에서는 한 기능의 오류가 전체 서비스를 마비시킬 수 있습니다. 

실제 예를 들어보겠습니다. 만약 결제 모듈에 버그가 발생하면 어떻게 될까요? 결제 처리가 느려지거나 멈추면, 그것이 전체 애플리케이션의 메모리를 소진시켜 차량 조회, 위치 추적, 심지어 이미 대여 중인 사용자의 반납 기능까지 모두 영향을 받게 됩니다.

2019년 국내 한 공유 킥보드 업체는 결제 시스템 장애로 2시간 동안 전체 서비스가 중단된 사례가 있습니다. 단 하나의 기능 오류가 전체 비즈니스에 치명적인 영향을 준 것입니다.

또한 시스템 일부를 수정할 때마다 전체를 재배포해야 하므로, 작은 버그 수정도 전체 서비스 중단 시간이 필요합니다.

**[문제 4: IoT 디바이스 통합의 복잡성]**

네 번째는 다양한 IoT 디바이스 통합의 복잡성입니다.

공유 모빌리티 업체들은 여러 제조사의 킥보드와 자전거를 사용합니다. 예를 들어, A 제조사는 HTTP API로 통신하고, B 제조사는 MQTT 프로토콜을 사용하며, C 제조사는 Bluetooth를 사용합니다.

문제는 이런 차이가 핵심 비즈니스 로직, 즉 대여 규칙이나 요금 계산 로직과 강하게 결합되어 있다는 것입니다.

새로운 제조사의 킥보드를 추가하려면, 그들의 통신 프로토콜에 맞춰 전체 시스템을 수정해야 합니다. 심지어 기존 제조사가 API를 변경하면, 그것 때문에 전체 시스템을 다시 배포해야 하는 상황이 발생합니다.

이는 시스템의 유연성을 크게 저해하고, 유지보수 비용을 급격히 증가시킵니다.

**[문제 요약]**

정리하면, 현재 공유 모빌리티 시스템은 실시간성 부족, 확장성 제한, 장애 전파 위험, 그리고 외부 의존성 관리의 어려움이라는 네 가지 핵심 문제를 안고 있습니다.

## 📌 슬라이드 4: As-Is vs To-Be 비교 (1분 30초)

이제 이러한 문제들을 어떻게 해결할 수 있는지 살펴보겠습니다.

**[As-Is 설명]**

왼쪽의 As-Is 모델을 보시면, 모든 기능이 하나의 통합된 시스템에 결합되어 있습니다. 차량 관리, 대여 처리, 위치 추적, 배터리 관리가 모두 하나의 애플리케이션 안에 있습니다.

이는 초기 개발은 빠르지만, 앞서 말씀드린 확장성 제한, 장애 전파, 유지보수의 어려움이라는 문제를 야기합니다.

**[To-Be 설명]**

반면 오른쪽의 To-Be 모델은 Microservices 아키텍처를 적용한 구조입니다.

각 기능을 독립적인 서비스로 분리했습니다. 차량 관리 서비스, 대여/반납 서비스, 위치 추적 서비스, 배터리 관리 서비스, 사용자 서비스가 각각 독립적으로 개발되고 배포됩니다.

이렇게 분리하면 어떤 장점이 있을까요?

첫째, 독립적인 확장이 가능합니다. 출퇴근 시간에는 대여 서비스만 3배로 확장하고, 다른 서비스는 그대로 유지할 수 있습니다.

둘째, 장애가 격리됩니다. 결제 서비스에 문제가 생겨도, 차량 조회와 반납은 정상적으로 작동합니다.

셋째, 유지보수가 쉬워집니다. 배터리 관리 로직을 수정할 때, 해당 서비스만 배포하면 됩니다.

## 📌 슬라이드 5: Microservices Architecture (2분)

그럼 첫 번째 아키텍처 패턴인 Microservices에 대해 자세히 설명하겠습니다.

**[서비스 구성 설명]**

저희는 시스템을 5개의 핵심 서비스로 분리했습니다.

차량 관리 서비스는 차량 등록, 상태 관리, 고장 처리를 담당합니다.

대여/반납 서비스는 실제 대여 트랜잭션과 결제를 처리합니다.

위치 추적 서비스는 실시간으로 GPS 데이터를 수집하고 사용자에게 제공합니다.

배터리 관리 서비스는 각 차량의 배터리 상태를 모니터링하고 충전이 필요한 차량을 식별합니다.

마지막으로 사용자 서비스는 회원 인증과 프로필을 관리합니다.

**[설계 근거 설명]**

이렇게 설계한 근거를 말씀드리겠습니다.

첫째, 독립적인 확장성입니다. 출퇴근 시간대에는 대여 요청이 폭증하지만, 다른 서비스의 부하는 크게 변하지 않습니다. 따라서 대여 서비스만 선택적으로 3배 확장하면 됩니다. 이를 통해 리소스 효율을 30% 향상시킬 수 있습니다.

둘째, 장애 격리입니다. 만약 결제 모듈에 오류가 발생해도, 사용자는 여전히 주변 킥보드를 조회할 수 있고, 이미 대여 중인 사용자는 정상적으로 반납할 수 있습니다. 한 서비스의 장애가 다른 서비스에 영향을 주지 않습니다.

셋째, 독립적인 배포입니다. 배터리 알고리즘을 개선하려면, 배터리 관리 서비스만 수정하고 배포하면 됩니다. 다른 서비스는 전혀 영향을 받지 않으므로, 배포 주기를 주 1회에서 일 3회로 단축할 수 있습니다.

**[효과]**

결과적으로, 동시 사용자 처리 능력을 1천 명에서 1만 명 이상으로 10배 향상시킬 수 있습니다.

## 📌 슬라이드 6: Event-Driven Architecture (2분)

두 번째 아키텍처 패턴은 Event-Driven Architecture입니다.

**[이벤트 흐름 설명]**

화면의 예시를 보시겠습니다. 

사용자가 킥보드를 반납하면, "반납 완료"라는 이벤트가 발생합니다. 이 이벤트는 Message Queue를 통해 여러 서비스로 전파됩니다.

위치 서비스는 이 이벤트를 받아 지도상의 차량 위치를 업데이트합니다.

대여 서비스는 차량 상태를 "대여 중"에서 "대여 가능"으로 변경합니다.

배터리 서비스는 반납 시점의 배터리 잔량을 체크합니다.

통계 서비스는 이 대여 건을 이용 기록에 추가합니다.

중요한 점은, 이 모든 처리가 **동시에, 독립적으로** 이루어진다는 것입니다.

**[기존 방식과의 차이]**

만약 기존의 동기 방식이었다면 어떻게 됐을까요?

대여 서비스가 반납을 처리한 후, 위치 서비스를 호출하고, 그 다음 배터리 서비스를 호출하고, 마지막으로 통계 서비스를 호출해야 합니다. 

만약 배터리 서비스가 느려지면? 전체 반납 처리가 지연됩니다. 

만약 통계 서비스가 다운되면? 반납 자체가 실패할 수 있습니다.

하지만 Event-Driven 방식에서는, 각 서비스가 이벤트를 비동기적으로 처리하므로, 한 서비스의 지연이나 장애가 다른 서비스에 영향을 주지 않습니다.

**[설계 근거]**

이렇게 설계한 근거는 세 가지입니다.

첫째, 비동기 처리로 응답 속도가 5배 향상됩니다. 사용자는 반납 버튼을 누르면 즉시 "반납 완료" 응답을 받고, 나머지 처리는 백그라운드에서 진행됩니다.

둘째, 느슨한 결합입니다. 서비스들이 직접 서로를 호출하지 않고, 이벤트를 통해서만 통신합니다. 따라서 서비스 간 의존성이 제거됩니다.

셋째, 확장이 매우 쉽습니다. 만약 새로운 기능, 예를 들어 "프로모션 서비스"를 추가하고 싶다면? "반납 완료" 이벤트를 구독하기만 하면 됩니다. 기존 코드는 전혀 수정하지 않아도 됩니다.

**[기술 스택]**

이를 구현하기 위해 Apache Kafka나 RabbitMQ 같은 Message Queue를 사용합니다.

## 📌 슬라이드 7: Hexagonal Architecture (2분 30초)

세 번째 아키텍처 패턴은 Hexagonal Architecture, 즉 포트-어댑터 패턴입니다.

**[문제 상황 재확인]**

앞서 말씀드린 네 번째 문제를 다시 떠올려보겠습니다. 

공유 모빌리티 업체는 여러 제조사의 차량을 사용합니다. A사는 HTTP로, B사는 MQTT로, C사는 Bluetooth로 통신합니다.

**[Hexagonal 구조 설명]**

Hexagonal Architecture는 이 문제를 해결합니다.

중앙에 비즈니스 로직, 즉 Core가 있습니다. 여기에는 "배터리가 20% 이상이어야 대여 가능", "요금은 분당 100원" 같은 핵심 규칙들이 있습니다.

이 Core와 외부 세계 사이에 Port라는 인터페이스가 있습니다. Port는 "무엇을 할 수 있는가"만 정의합니다.

예를 들어, "IoTDevicePort"라는 인터페이스는 이렇게 정의됩니다:
- getBatteryLevel(): 배터리 잔량을 가져온다
- getLocation(): 위치를 가져온다
- lockVehicle(): 차량을 잠근다

핵심은, 이 인터페이스가 "어떻게" 하는지는 모른다는 것입니다. HTTP든 MQTT든 Bluetooth든 상관없습니다.

그리고 각 제조사별로 Adapter를 만듭니다. Adapter A는 HTTP를 사용해서 이 인터페이스를 구현하고, Adapter B는 MQTT를 사용해서 구현합니다.

**[코드 예시 설명]**

화면의 코드를 보시면, IoTDevicePort 인터페이스가 정의되어 있습니다.

비즈니스 로직은 이 인터페이스만 알면 됩니다. 실제 통신이 어떻게 이루어지는지는 전혀 몰라도 됩니다.

**[설계 근거]**

이 패턴의 장점은 세 가지입니다.

첫째, 추상화입니다. 비즈니스 로직이 외부 기술로부터 완전히 분리됩니다. 대여 규칙은 킥보드든 자전거든, HTTP든 MQTT든 동일하게 적용됩니다.

둘째, 교체 가능성입니다. 제조사를 변경하거나 추가할 때, Adapter만 새로 만들면 됩니다. 핵심 비즈니스 로직은 한 줄도 수정하지 않아도 됩니다.

셋째, 테스트 용이성입니다. 실제 IoT 디바이스가 없어도, Mock Adapter를 만들어서 모든 기능을 테스트할 수 있습니다.

**[효과]**

결과적으로, 신규 차량 타입을 추가하는 개발 시간을 80% 단축할 수 있습니다. 기존에는 3일이 걸렸다면, 이제는 하루 만에 새 제조사를 추가할 수 있습니다.

## 📌 슬라이드 8: 핵심 기술 문제 및 해결방안 (2분)

이제 이 프로젝트의 가장 어려운 기술적 문제와 해결 방법을 말씀드리겠습니다.

**[핵심 문제 제시]**

Microservices로 시스템을 나누면 새로운 문제가 생깁니다. 바로 **분산 트랜잭션 관리**입니다.

예를 들어볼까요? 사용자가 차량을 반납하면:
1. 위치 서비스가 지도를 업데이트해야 하고
2. 대여 서비스가 상태를 변경해야 하고
3. 배터리 서비스가 배터리를 체크해야 합니다

만약 2번이 실패하면 어떻게 될까요? 1번은 이미 완료됐는데, 차량 상태는 여전히 "대여 중"입니다. 데이터 불일치가 발생합니다.

전통적인 데이터베이스 트랜잭션으로는 이를 해결할 수 없습니다. 왜냐하면 각 서비스가 서로 다른 데이터베이스를 사용하기 때문입니다.

**[해결 방법 1: Saga Pattern]**

첫 번째 해결 방법은 Saga Pattern입니다.

Saga는 분산 트랜잭션을 여러 단계로 나누고, 각 단계마다 **보상 트랜잭션**을 정의합니다.

예를 들어:
- Step 1: 위치 업데이트 → 실패 시 보상: 위치 롤백
- Step 2: 상태 변경 → 실패 시 보상: 상태 원복 + 위치 롤백
- Step 3: 배터리 체크 → 실패 시 보상: 전체 롤백

만약 Step 3가 실패하면, 시스템은 자동으로 Step 2와 Step 1의 보상 트랜잭션을 실행해서 데이터를 원래대로 되돌립니다.

**[해결 방법 2: Event Sourcing]**

두 번째는 Event Sourcing입니다.

모든 상태 변경을 이벤트로 기록합니다. "차량 1234번이 오전 9시에 대여됨", "차량 1234번이 오전 9시 30분에 반납됨" 같은 식으로요.

이렇게 하면, 언제든 이벤트 기록을 재생해서 현재 상태를 복구할 수 있습니다. 또한 모든 변경 이력이 남아서 문제 추적이 쉽습니다.

**[해결 방법 3: Idempotency]**

세 번째는 멱등성(Idempotency) 보장입니다.

네트워크 문제로 같은 이벤트가 두 번 전달될 수 있습니다. 예를 들어 "반납 완료" 이벤트가 중복으로 올 수 있죠.

멱등성을 보장한다는 것은, 같은 이벤트를 여러 번 처리해도 결과가 동일하다는 뜻입니다. 이를 위해 각 이벤트에 고유 ID를 부여하고, 이미 처리한 이벤트는 무시합니다.

**[해결 방법 4: Partition Key]**

마지막으로, Kafka의 Partition 메커니즘을 활용합니다.

같은 차량에 대한 모든 이벤트는 같은 Partition으로 보내서, 이벤트 순서를 보장합니다. "대여" 이벤트가 "반납" 이벤트보다 먼저 처리되도록 하는 거죠.

# 📋 예상 질문 및 답변

## Q1: "왜 Monolithic이 아니라 Microservices를 선택했나요? 초기에는 Monolithic이 더 간단하지 않나요?"

**답변:**

좋은 질문입니다. 맞습니다, 초기 개발 단계에서는 Monolithic이 더 간단하고 빠를 수 있습니다.

하지만 본 프로젝트의 목표는 "재사용성과 유지보수성을 높이는 아키텍처 설계"입니다. 공유 모빌리티 시스템은 다음과 같은 특성이 있습니다:

1. **비대칭적 트래픽**: 대여는 출퇴근 시간에 집중되지만, 위치 조회는 24시간 지속됩니다.
2. **독립적인 업데이트 주기**: 배터리 알고리즘은 자주 개선되지만, 결제 로직은 거의 변경되지 않습니다.
3. **외부 의존성**: IoT 디바이스, 결제 시스템 등 외부 시스템과의 통합이 많습니다.

이런 특성을 고려하면, 초기부터 Microservices로 설계하는 것이 장기적으로 더 효율적입니다. 

물론 처음부터 완전한 Microservices를 구축하기보다는, 핵심 서비스 3-5개로 시작해서 점진적으로 확장하는 전략을 취할 것입니다.

---

## Q2: "Event-Driven에서 이벤트 순서를 어떻게 보장하나요?"

**답변:**

매우 중요한 질문입니다. 이벤트 순서 보장은 두 가지 방법으로 해결합니다.

첫째, **Kafka의 Partition 메커니즘**을 활용합니다. 같은 차량 ID를 Partition Key로 사용하면, 해당 차량의 모든 이벤트가 같은 Partition에 순서대로 저장됩니다. 예를 들어, 차량 1234번의 "대여" → "이동" → "반납" 이벤트가 발생 순서대로 처리됩니다.

둘째, **Event Sourcing**을 적용합니다. 각 이벤트에 타임스탬프와 시퀀스 번호를 부여합니다. 만약 이벤트가 순서 없이 도착하면, 컨슈머에서 버퍼링했다가 순서대로 재정렬해서 처리합니다.

또한 **Idempotency**를 보장해서, 만약 같은 이벤트가 중복으로 오거나 순서가 뒤바뀌어도 시스템 상태가 손상되지 않도록 설계합니다.

---

## Q3: "Hexagonal Architecture가 기존 Layered Architecture와 어떻게 다른가요?"

**답변:**

좋은 비교입니다. 

**전통적인 Layered Architecture**는 Presentation → Business → Data Access 순으로 위에서 아래로 흐릅니다. 상위 계층이 하위 계층에 의존하죠.

문제는 Business Layer가 Data Access Layer에 강하게 의존한다는 것입니다. 예를 들어, MySQL을 MongoDB로 바꾸려면 Business Layer도 수정해야 합니다.

**Hexagonal Architecture**는 이를 뒤집습니다. Business Logic이 중심에 있고, 외부 세계(DB, UI, IoT 등)가 Business Logic에 맞춰 Adapter를 구현합니다.

핵심 차이는 **의존성의 방향**입니다. Layered는 Business가 Infrastructure에 의존하지만, Hexagonal은 Infrastructure가 Business에 의존합니다.

실제 예를 들면:
- Layered: "대여 로직이 PostgreSQL 쿼리를 직접 실행"
- Hexagonal: "대여 로직이 'VehicleRepository' 인터페이스를 호출, PostgreSQL Adapter가 이를 구현"

이렇게 하면 데이터베이스를 바꿔도 비즈니스 로직은 전혀 수정하지 않아도 됩니다.

---

## Q4: "실제 구현 시 가장 어려울 것 같은 부분은 무엇인가요?"

**답변:**

솔직히 말씀드리면, **분산 트랜잭션 관리**가 가장 어려울 것으로 예상됩니다.

슬라이드 8에서 설명한 Saga Pattern은 개념적으로는 명확하지만, 실제로 구현하려면 고려할 사항이 많습니다.

예를 들어:
1. 보상 트랜잭션이 실패하면? (보상의 보상?)
2. 일부 서비스가 응답하지 않으면?
3. 네트워크 지연으로 이벤트 순서가 뒤바뀌면?

이를 해결하기 위한 저희 전략은:

**첫째, 단계적 접근**입니다. 처음에는 간단한 시나리오(대여-반납)부터 구현하고, 점차 복잡한 케이스를 추가합니다.

**둘째, 기존 프레임워크 활용**입니다. Eventuate Tram 같은 검증된 Saga 구현 라이브러리를 사용해서 바퀴를 재발명하지 않습니다.

**셋째, 철저한 테스트**입니다. Chaos Engineering 기법을 사용해서 네트워크 장애, 서비스 다운 등을 시뮬레이션하고 시스템의 복원력을 검증합니다.

물론 시간이 부족하면, 먼저 핵심 기능을 Eventually Consistent하게 구현하고, Saga는 추후 개선 항목으로 남겨둘 수도 있습니다.

## Q5: "Redis Cache를 사용하면 데이터 불일치 문제가 생기지 않나요?"

**답변:**

네, 맞습니다. Cache는 항상 데이터 불일치의 위험이 있습니다.

하지만 공유 모빌리티 시스템의 특성을 고려하면, **약간의 지연은 허용 가능**합니다.

예를 들어:
- 차량이 반납된 후 지도에 표시되기까지 1-2초 지연 → 허용 가능
- 배터리가 19%인데 20%로 표시 → 허용 가능 (어차피 곧 업데이트됨)

하지만 **중요한 데이터는 Cache를 거치지 않습니다**:
- 실제 대여/반납 트랜잭션 → 데이터베이스에 직접 저장
- 결제 정보 → Cache 사용 안 함

우리가 Cache하는 것은:
- 차량 위치 (30초마다 업데이트)
- 차량 상태 (대여 가능/불가능)
- 배터리 잔량

**Cache 무효화 전략**:
- 차량 상태가 변경되면 즉시 해당 Cache 삭제
- TTL(Time To Live) 설정: 위치는 30초, 상태는 10초
- Event-Driven으로 상태 변경 이벤트 받으면 Cache 갱신

또한 Cache Miss 시의 Fallback도 구현합니다. Redis가 다운되어도 시스템은 느려질 뿐 중단되지 않습니다.

## Q6: "이 아키텍처를 다른 도메인에도 적용할 수 있나요?"

**답변:**

네, 충분히 가능합니다. 이 아키텍처 패턴들은 다음과 같은 특성을 가진 시스템에 적합합니다:

**1. Microservices가 적합한 경우:**
- 시스템의 일부만 높은 트래픽을 받는 경우
- 팀이 여러 개로 나뉘어 독립적으로 개발하는 경우
- 각 기능의 업데이트 주기가 다른 경우

예: 전자상거래(상품 조회 vs 결제), 소셜 미디어(피드 vs 메시징)

**2. Event-Driven이 적합한 경우:**
- 실시간 처리가 중요한 경우
- 여러 시스템이 같은 이벤트에 반응해야 하는 경우
- 시스템 간 결합도를 낮추고 싶은 경우

예: 주문 시스템(주문 → 재고, 결제, 배송, 알림), 스마트 홈(센서 → 제어, 로깅, 알림)

**3. Hexagonal이 적합한 경우:**
- 외부 시스템/디바이스 통합이 많은 경우
- 외부 의존성이 자주 변경되는 경우
- 비즈니스 로직을 명확히 분리하고 싶은 경우

예: 결제 시스템(여러 PG사 통합), 배송 시스템(여러 택배사 통합)

실제로 이 패턴들은 Netflix, Uber, Airbnb 등에서 널리 사용되고 있습니다.

## Q8: "Kubernetes가 꼭 필요한가요? Docker Compose로는 안 되나요?"

**답변:**

개발 단계에서는 Docker Compose로도 충분합니다.

실제로 저희 계획은:
- **개발/테스트 환경**: Docker Compose 사용
- **프로덕션 시뮬레이션**: Kubernetes 사용 (선택 사항)

Docker Compose의 장점:
- 설정이 간단함
- 로컬 개발에 최적화
- 학습 곡선이 낮음

Kubernetes의 장점:
- 자동 스케일링
- 자가 치유 (Self-Healing)
- 롤링 업데이트
- 프로덕션 수준의 오케스트레이션

본 프로젝트는 "아키텍처 설계"에 초점이 있으므로, Docker Compose로 Microservices의 독립적 배포와 스케일링을 충분히 시연할 수 있습니다.

만약 시간이 남으면, Kubernetes로 마이그레이션해서 실제 프로덕션 환경을 시뮬레이션해볼 수도 있습니다. 하지만 이는 필수가 아닌 추가 목표입니다.
